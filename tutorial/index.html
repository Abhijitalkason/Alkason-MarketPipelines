01 — Foundations

What is MLOps, and why does it exist?

MLOps is DevOps for machine learning: the practices that take a model from a notebook experiment to a reliable, monitored, reproducible system people can trust — and keep trustworthy as the world changes.

Why does ML need its own discipline? Start with how it differs from ordinary software.

λTraditional software

Behavior is written by a human as explicit rules. Same input → same output. You version code. A passing test stays passing — logic doesn't rot on its own.

∑Machine learning

Behavior is learned from data. The "logic" is numbers fit to examples. You must version code + data + model + config together — and a model accurate last month can silently decay as the world drifts.

The hidden technical debt of ML

A landmark Google paper put it bluntly: in a real ML system the model is a tiny box surrounded by data collection, feature engineering, validation, serving, monitoring, and configuration — and that surrounding machinery is where systems actually fail. MLOps is the engineering of that machinery.

The core problem MLOps solves

A model is only as good as the process that produced it and the guarantees around it. Can you reproduce it exactly? Prove it never saw the future in training? Tell when it stops working? Roll it back safely? MLOps answers all four.

The machine-learning lifecycle

Every ML system moves through a loop. MLOps makes each arrow automated, versioned, and observable instead of a manual step in someone's head.

The lifecycle loop

02 — The building blocks

The jobs of an MLOps stack

There's no single "MLOps tool" — it's a set of jobs, each with its own tooling. Here are the eight, each mapped to the exact tool this project uses.

1Data versioning

Snapshot the exact data a model trained on, so results reproduce. → DVC tracks big data/model files; git tracks the small pointer files.

2Experiment tracking

Log every run's params, metrics, artifacts. → MLflow, tagging each run with its git SHA + config hash.

3Model registry

A versioned catalog with Staging → Production stages + rollback. → MLflow Registry. The API serves whatever is in Production.

4Pipelines & CI

Turn "run the notebook" into a deterministic, testable pipeline. → a CLI (main.py --mode …) + pytest, offline fixtures.

5Serving

Expose the model behind a stable, secured interface. → FastAPI + Swagger, API-key protected, inference off the event loop.

6Monitoring & drift

Detect when live data drifts from training data. → Evidently reports that can force recalibration or halt.

7Explainability

Explain each decision. → SHAP attributions + an IBM Granite LLM (via Ollama) for plain-English "why".

8Packaging

Ship it identically everywhere. → Docker Compose wires MLflow, the API, and Ollama.

Plus the modeling libraries: LightGBM & CatBoost (learners), Optuna (tuning), scikit-learn (calibration & metrics), FinBERT (news sentiment).

04 — The governing idea

Engineer the win rate; ask the model only for an edge

Most people build a model that's accurate. This system does something subtler: it engineers the win rate with the geometry of the trade and asks the model only to add a small edge on top.

Suppose every trade has a profit target of a×ATR and a stop-loss of b×ATR. (ATR = a stock's typical daily move.) If price were a pure coin-flip, the chance of hitting the target before the stop is pure geometry:

baseline_win_rate = b / (a + b)          # wide stop + narrow target ⇒ high win rate…
                                         # …but each loss is big. Expectancy is what pays:
EV = delta * (a + b) * ATR - cost      # delta = the model's edge, in win-rate points

At the no-edge baseline, expectancy is exactly −cost. Every rupee of profit must come from delta — the model nudging the win rate above what geometry alone gives. That's the model's only job. Move the sliders:

The frozen contract

Success was defined in advance as two numbers: win rate ≥ 80% on emitted signals AND post-cost expectancy ≥ +0.10%/trade — long-only (retail can't hold overnight shorts on NSE). The model can't move the goalposts later.

Point-in-time correctness: the cardinal sin of time-series ML

The commonest way financial ML "works" in a backtest and then loses money live is lookahead leakage: training on information that wasn't available yet. A feature computed at Monday's close must use only Monday-and-before — never a peek at Tuesday. This project enforces PIT structurally:

  • Trailing-only windows. Every feature (ATR, RSI, momentum, z-scores) is strictly causal — a row dated D uses only data ≤ D.
  • Survivorship-free universe. The tradeable list is recomputed monthly from trailing turnover, so history is judged by what was liquid then.
  • Release timestamps. Global data carries a release_ts (US closes become public ~02:30 IST next day). Features filter on release_ts ≤ decision_ts.
  • Imputation is never disguised. A missing optional feature becomes NaN→0 plus a _present=0 flag — so the model can tell "zero" from "absent".
Go deeper — the fixed feature schema & the serve-time guardsrc/daily/features.py

The schema is versioned and fixed (SCHEMA_VERSION = "daily-v1"): 17 required market features + 22 optional (3 F&O + 11 global + 5 macro + 3 sentiment) + 22 _present flags = 61 columns, always in the same order. The "present" trick:

missingness — value AND a presence flag travel togetherfor f in FNO_FEATURES:
    out[f] = np.nan
    out[f + "_present"] = 0.0

def impute_optional(df):
    # optional NaN → 0.0, paired with the (already-0) _present flag
    out = df.copy()
    out[OPTIONAL_FEATURES] = out[OPTIONAL_FEATURES].fillna(0.0)
    return out

And a guard runs before every single prediction — backtester, screener, and API alike. Train/serve can't silently diverge:

check_schema — called before EVERY predictdef check_schema(df):
    missing = [c for c in FEATURE_ORDER if c not in df.columns]
    if missing: raise FeatureSchemaError(f"missing columns {missing}")
    if [c for c in df.columns if c in FEATURE_ORDER] != FEATURE_ORDER:
        raise FeatureSchemaError("column order mismatch")
    bad = df[MARKET_FEATURES].isna().any()
    if bad.any(): raise FeatureSchemaError(f"NaN in market features {list(bad[bad].index)}")
Why this is the load-bearing test

The repo's most important test is test_no_lookahead_property. If one feature ever peeked at the future, every downstream number — win rate, expectancy, the whole gate — would be fiction. PIT discipline is what makes the metrics mean anything.

From raw ticks to a ranked list

Here's the full journey a trading day takes. Each stage is a real module in src/daily/. This is the pipeline — automated, versioned, observable end to end.

5

A gradient-boosted tree classifier predicts P(win). Tuned with Optuna — only on an inner split of the training fold, never the data used to score it.

6

Raw scores aren't true probabilities. Isotonic calibration maps them so "70%" really wins ~70% of the time. Section 08.

7

The screener ranks the universe, attaches a SHAP "why" and a trade plan, emits the top-N. Then evaluate.py scores every past pick against what actually happened.

Train == Serve, by construction

A subtle production bug: the code that trains and the code that serves drift apart, so live features differ from training features. Defeated here by using the identical fit protocol in training and backtesting (head → calibrate → refit on the full window with frozen params) and recording the exact feature-flags a model trained under — warning loudly if serving config differs.

07 — Deep dive

Triple-barrier labeling, animated

"What is a win?" is a design decision, not a given. The triple-barrier method answers it by simulating the trade. Watch a decision play out:

Interactive · Triple-barrier labeler

Press replay to simulate a trade.
  • TARGET upper line at entry + a×ATR. Touch first → win (1).
  • STOP lower line at entry − b×ATR. Touch first → loss (0).
  • TIME the right edge, N sessions later. Neither touched → label by up/down.

Two honesty rules matter enormously: entry is the next session's open (never the close you just observed), and a bar touching both barriers counts pessimistically as the stop. Optimistic labeling is how backtests lie. Here's the real code:

src/daily/labeler.py — first-touch scan, conservative on dual-touchdef _resolve_daily_path(path, entry, target, stop):
    for ts, bar in path.iterrows():
        hit_t, hit_s = bar.high >= target, bar.low <= stop
        if hit_s:                      # dual-touch or stop-only → pessimistic
            return ts, stop, "stop"
        if hit_t:
            return ts, target, "target"
    last = path.iloc[-1]
    return path.index[-1], float(last.close), "time"
the label rule (entry = NEXT session open, not today's close)entry  = float(df.iloc[i + 1]["open"])
target = entry * (1 + hc["target_atr"] * a)
stop   = entry * (1 - hc["stop_atr"]  * a)
exit_ts, exit_price, barrier = _resolve_daily_path(path, entry, target, stop)
pnl_pct = (exit_price - entry) / entry
label = int(pnl_pct > 0) if barrier == "time" else int(barrier == "target")

Choosing a and b sets the baseline win rate before the model does anything — which is exactly why the geometry calculator is the pivot of the whole design.

08 — Trustworthy probabilities

Calibration: making "70%" mean 70%

A model outputs a score between 0 and 1 — but raw scores are not real probabilities. A model can be 90% "confident" and right only 60% of the time. If you're going to gate on probability, you must first make the probability honest.

A reliability diagram shows the problem: bucket predictions by their score (x-axis) and plot how often they actually came true (y-axis). Perfect calibration lies on the diagonal. Drag the slider to make the model over/under-confident, then calibrate it:

Interactive · Reliability diagram & isotonic calibration

raw model (miscalibrated) after isotonic perfect (diagonal)

Isotonic regression is the fix: it learns a monotonic (only-ever-increasing) step function mapping raw scores to true frequencies. It's non-parametric — it bends to whatever shape the miscalibration takes, as long as "higher score ⇒ higher truth" holds. The real code is tiny:

src/intraday/blend.py — reused by the daily systemdef fit_calibration(self, p_blend, y):
    # isotonic on the OUT-OF-FOLD calibration tail — never on in-fold preds
    self.calibrator = IsotonicRegression(y_min=0.0, y_max=1.0, out_of_bounds="clip")
    self.calibrator.fit(p_blend, y)

def calibrated(self, p_price, p_flow=None):
    p = self.blend(p_price, p_flow)
    return self.calibrator.predict(p)
The subtle discipline

Calibration is fit on an out-of-fold tail the model never trained on — fitting it on in-fold predictions would learn the model's memorized answers, not its real behavior. When two model channels exist (price + flow) a tiny grid-search picks the blend weight by log-loss first; with the flow channel off, the weight is pinned to 1.0 and only the isotonic step remains.

09 — The decision to stay silent

The adaptive conformal gate

Now that probabilities are honest, we need a rule for when to speak. Firing on everything above a fixed 0.80 is brittle — markets shift, and a stale threshold either over-fires (too many losers) or under-fires (misses everything). Adaptive Conformal Inference (ACI) makes the threshold self-correct to hold a target error rate.

The idea (a form of the Gibbs–Candès online update): pick a target error budget α (here 0.20, i.e. aim for an 80% win rate). Start the threshold τ a little high. After each day's fired signals mature, nudge τ: if realized error beat the budget, lower the bar; if it overshot, raise it. Watch it converge:

Here's the actual update and fire logic — the whole gate is about 20 lines:

src/intraday/conformal_gate.py — the adaptive updatedef update(self, fired_labels):
    if fired_labels:
        err = 1.0 - float(np.mean(fired_labels))          # realized error among fired
        self.state.tau = float(np.clip(
            self.state.tau + self.state.gamma * (err - self.state.alpha),
            0.5, 0.995))                              # err>α ⇒ τ rises (fewer, safer)
    return self.state.tau
the fire decision — τ AND a per-model agreement floordef fire(self, p_cal, p_price, p_flow=None):
    mask = (p_cal >= self.state.tau) & (p_price >= self.floor)   # floor = 0.75
    if self.flow_active and p_flow is not None:
        mask &= p_flow >= self.floor
    return mask
Config (config_v3.yaml)

target_win_rate: 0.80 → α = 0.20 · fire_threshold_init: 0.84 (a few points high so it relaxes to equilibrium) · aci_gamma: 0.01 · model_agreement_floor: 0.75. τ is clipped to [0.5, 0.995]. (The demo above uses a larger γ so it converges on-screen in 60 days.)

10 — Getting the truth

Validation you can trust: walk-forward & leakage traps

On time series, ordinary cross-validation lies — shuffling rows lets the model train on the future and test on the past. The honest method is walk-forward.

Interactive · Purged, embargoed walk-forward

train (past only) embargo gap test (out-of-sample)

Three defenses make it honest:

  • Walk forward. Always train on the past, test on the immediate future, then roll. Here, ≥6 folds.
  • Purge & embargo. Labels look several days ahead (the trade horizon), so training rows whose outcome overlaps the test window are purged, and an embargo gap longer than the horizon sits between train and test — killing the leakage overlapping labels create.
  • The leakage alarm. If out-of-sample AUC ever comes back above 0.80, the backtester refuses the run — for this problem a score that good almost certainly means the future leaked in. Suspiciously good results are treated as bugs.

Why calibration & day-clustering matter

Confidence intervals are computed day-clustered: because regime features are constant across all of a day's signals, those signals aren't independent — naive statistics would overstate confidence. Clustering by day tells the truth about how much you really know.

The diagnostic that was retired

Plain accuracy at 100% coverage was banned as a decision metric. A selective system is designed to look near-random when forced to score everything — ≈0.50 there is expected, not failure. The only metrics that count are the win rate and expectancy of the signals it chose to emit.

11 — The climax

The gates — and the day the system killed itself

This is what makes the project a genuine MLOps lesson, not just an ML demo. Success and failure were defined in advance, hard-coded into the source so they couldn't be tuned after seeing results.

Phase 0: measure first, build never

Every earlier version made the same mistake — build first, measure later. So v6 inverted it. Before writing any model code, it ran a pure measurement: 48 geometry "cells" (every combination of target width, stop width, holding period) scored across 1.54 million rows and 2,906 symbols, judged against a gate frozen before anyone saw a number.

"Selective-signal-by-geometry does not work, long-only, on NSE, at holds of five days or less." Later reproduced bit-for-bit. The team declined to tune the thresholds to force a pass — that would be lying — and stopped.

The most important lesson in this tutorial

A KILL is a successful outcome. The system did its job: it answered the load-bearing question cheaply, honestly, and before any capital was at risk. Shipping a real "no" is infinitely more valuable than shipping a false "yes." The product was never the model — it was the gate that could say no.

14 — Confidence in the code

Testing & reproducibility

In a real-money system, a bug isn't a glitch — it's a false signal. Tests here aren't a formality; several are load-bearing, guarding the exact traps that would silently corrupt every downstream number.

No-lookahead

test_no_lookahead_property — a property test that would catch any feature peeking at the future (bug class B-4).

Regime PIT

test_regime — the regime channel's lookahead exclusion, veto logic, and news degradation.

Labeler geometry

test_geometry_v4 — the labeler override that, if broken, would have silently corrupted every grid sweep.

There's also a dead-control sweep — an unusual, sharp idea. It fails the build if any safety control loses its live call site, or if any deleted legacy module is still referenced:

Go deeper — the dead-control & dead-import sweeptests/test_dead_controls.py

test_controls_have_external_call_sites fails if any of these lose an external caller — a control that isn't called is worse than no control, because it looks like protection:

check_kill_switches (risk.py)   cross_check_bhavcopy (bars.py)
run_check           (drift.py)  reconcile_day        (data_feed.py)
tune                (price_model.py)  check_schema    (features.py)

test_no_v1_module_references fails if any decommissioned v1 module (xgboost_model, lstm_model, chronos_model, ensemble_model, news_scraper, …) is still imported anywhere — so a killed approach can't linger as zombie code.

The whole suite runs on deterministic synthetic fixtures with no network, and Gate 0 requires it all green at ≥85% coverage. Reproducibility is the same story from the other side: every training run is tagged with its git SHA + config hash, data is DVC-pinned, and re-running Phase 0 in 2026 matched the committed KILL bit-for-bit.

The disclaimer, verbatim from the code

"Research aid, not investment advice. … this repo's measured record shows NO proven predictive edge for any model at these horizons. Verify every input via the reference links before acting; markets carry risk of loss."

That honesty is engineered in, not bolted on. This is what responsible ML in a high-stakes domain looks like.

16 — Takeaways

Nine MLOps lessons to carry away

Measure first

Answer the load-bearing question with the cheapest experiment, before you build.

Pre-register success

Freeze the metric & threshold before results, so you can't move the goalposts.

PIT or nothing

On time series, structural no-lookahead is the line between science and fiction.

Train == serve

Identical fit path in training and production; record the config gap.

Calibrate

An uncalibrated probability can't gate a decision. Isotonic maps scores to truth.

Validate honestly

Walk-forward, purge, embargo. Treat suspiciously good results as bugs.

Reproduce exactly

Version code + data + model + config together, or you have nothing.

Monitor as a kill-switch

Drift detection that can halt beats a dashboard nobody reads.

A "no" is a win

The gate that can honestly stop the project is the most valuable thing you build.
