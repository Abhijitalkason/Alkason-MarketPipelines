Answer 2: Separate files or combined?
Both — the pattern is "separate files on disk, combined per-row in memory." No source is pre-merged into one master file; each feed keeps its own file(s), and the feature builder pulls from all of them and merges into a single feature row at build time.

Intraday — 5 separate parquet sources, merged row-by-row in features.py:

Load bars (data/bars/<SYM>/<YYYY-MM>.parquet)      → 20 PRICE_FEATURES
  ├─ read fo_<date>.parquet (20 days)              → oi_change_z, basis_pct
  ├─ read eq_<date>.parquet (20 days)              → delivery_z
  ├─ read preopen/<date>.parquet (PIT <09:30)      → preopen_imbalance
  └─ read fii_dii.parquet                          → fii_5d_z
        → merged via `**flow` dict-unpack into ONE 31-column row
Daily — one partial pre-merge, then ~14 separate sources combined lazily:

One pre-merge step: panel.py:122 LEFT-JOINs eq_* + fo_* per symbol → data/daily/<SYM>.parquet (this is the only place files are physically combined).
Everything else stays separate and is combined in-memory per decision day via row.update(...) in features.py:334-346:
9 separate global files — spx.parquet, ndx.parquet, dxy.parquet, crude.parquet, gold.parquet, us10y.parquet, usdinr.parquet, asia.parquet, india_vix.parquet — each read independently by date, never joined to each other.
3 separate macro CSVs — macro_calendar.csv, events.csv, monsoon.csv.
1 FII file (fii_dii.parquet) + 1 sentiment file (scored.parquet).
Key architectural facts:

One file per source type, deliberately. This is why the _present flag exists: if a source file is absent (e.g. global data not yet ingested), that block imputes to 0 and flags _present=0 rather than failing — so sources are decoupled and independently optional.
Point-in-time enforced at merge: every non-bar source is filtered release_ts <= decision_ts (or strictly prior day) before it joins the row — no lookahead.
Intraday splits by channel into two models: PRICE_FEATURES → LightGBM, FLOW_FEATURES → CatBoost (deliberate decorrelation). Daily uses a single combined 61-feature row into one LightGBM.
Bottom line: the design is intentionally modular per source (separate files, independently ingested, independently optional), with combination happening at feature-build time — not a single monolithic input file. The trade-off is that several high-value categories (option-chain/PCR, real order-flow features, live news, real index/sector context) are either omitted or scaffolded-but-unwired, which is consistent with the project's measured finding that market+F&O alone showed no edge.
